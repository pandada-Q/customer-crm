## 1. 评估对象

为不懂技术的小企业负责人（王总）建设「客户资料管理助手」：AI 把多源多格式、带重复与字段冲突的零散客户资料规整为统一 schema、干净、带溯源的客户总表（冲突并列展示、人工在应用内待确认区拍板，绝不静默合并/丢弃），并配一个「静态前端 + 轻量后端 + 数据库」的公网应用持续承载数据与后续多批上传，附带合作意向客户识别、待办事项提取两项增强能力。

## 3. 价值结论

**值得做（有条件）。** 理由：落地成本低（轻量架构 + 无系统对接 + 无量化门槛）、客户意愿极强（主动投入、承担成本、已定责任分工）、可复制性高（可沉淀模板复用于海量同类小企业）。价值结论附带两个条件：

1. **收益不可量化，定价不宜按数据量/效果计费**——本单商业逻辑是"一次性规整费 + 新批次代管服务费"的轻量服务模式，以解决实际麻烦 + 持续省事为卖点，而非 ROI 型售卖；
2. **PII 公网暴露边界须在实施前与客户书面对齐**（单一口令的持有人范围、口令管理方式、数据留存位置），作为 D18① 的责任留痕。

## 4. 优先级建议

本 spec 为单项目、能力一体交付（非相互独立的多候选），故不做横向排序，给出**交付内的能力侧重排序**供 fde-to-tickets 参考：

| 候选 | 优先级 | 理由 |
|------|--------|------|
| 数据规整 + 待确认区拍板闭环（含去重/冲突/清洗/溯源） | 最高 | 项目骨架与验收核心（D12：去重规整 + 待确认区清零），是其余能力的数据基础 |
| 公网应用 + 新批次上传/合并服务闭环 | 高 | "持续投喂不乱"是客户长期价值与续费点，应用形态本身（D15）承载全部交互 |
| 合作意向客户识别 | 中高 | 业务上行空间最大（市场部跟进线索），实现成本低（复用既有字段信号 + 人工确认，D6） |
| 待办事项识别提取 | 中 | 低成本低风险增强，防遗忘体验好，但不构成主价值（D7 明确不泛抽取） |
| 修正指令识别（路径 B） | 低 | 仅在批量纠错场景启用，格式约定待定（D20），可后置或不做 |

## 5. 风险提示

- **PII 公网 + 单一口令**：无登录鉴权与人级区分（D18①），口令即唯一闸门。建议实施时与客户约定口令持有人清单与轮换机制，交付说明中明示"应用内数据按权限共享"，规避合规与误用争议。
- **长期服务依赖受托方**：应用代管、新批次合并、字段级纠错全部依赖受托方持续运营，客户无 IT、无自运维能力（D13/D20）。若服务中断，客户数据如何导出/接管未定义。建议在 5 项提交物中补一条**数据导出能力/导出说明**，或在交付时与客户书面约定服务终止时的数据归还路径。
- **后续批次质量不可控**：客户明示"以后的批次可能比这批还乱"（spec §8），D21 低置信兜底 + D17 分流可承接，但人工拍板负担会随批次增长。建议与客户约定单批规模节奏与"待确认区一周清零"的例行纪律（D19）。
