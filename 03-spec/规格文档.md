# 规格文档（Spec）：客户资料管理助手

> 生成日期：2026-09-05
> 项目类型：混合项目（软件 + AI）
> 由 fde-to-spec 生成，基于 02-requirements/收敛需求文档.md（5 轮澄清，21 项决策 D1–D21）
> 依据层级：本 spec 每章均引用 02 的决策/排除项编号，未在 02 中写明的实施细节一律标"待定"，不做臆造

## 1. 问题陈述

客户（王总）是一位不懂技术的小企业负责人，其团队（市场部同事等数人）平时各自用 Excel / JSON 导出 / 微信文本 / 老系统导出等不同方式分别收集客户资料，没有统一格式、没有统一录入流程。目前积压了**首批**约 20 人级、多人多源多格式的零散资料（含重复行、字段切坏、口语化表述、字段跨源冲突、占位行、夹杂非联系人事项等脏乱形态），无法直接使用。

王总需要的是：把首批资料**规整为一份统一、干净、带溯源、可直接使用**的客户数据，并配一个**公网可访问的应用**持续承载这批数据与后续多批补录，最终得到"以后能直接用"的结果。

## 2. 解决方案概述

建设一套「客户资料管理助手」：

- **数据侧**：由 AI 对首批多源资料做结构化抽取、跨源去重识别、字段冲突标注与清洗归一，产出统一 schema 的客户总表数据。**不做静默丢弃/静默合并**——所有冲突、疑似重复、低置信内容均以可追溯形式交给人工拍板。
- **应用侧**：部署一个公网可访问的应用，采用「静态前端 + 轻量后端 + 数据库」形态，承载：客户总表（搜索/筛选/查看）、待确认区（拍板/确认/低置信补录）、合作意向客户视图、待办页、新批次上传入口。上传新批次、冲突拍板、意向确认/驳回均**即时入库生效、页面刷新即见**，仅代码变更才重新部署。
- **交付侧**：向不懂技术的客户交付 5 项提交物（规整数据、公网应用、代码与运行说明、一页非技术说明、AI 协作日志），并提供持续的"新批次投喂→合并→拍板"服务闭环。

应用设**单一访问口令**（凡持口令者均可查看与执行有限操作），本版不做登录鉴权与人级权限区分。

## 3. 实施决策

决策均取自 02 收敛需求文档第 3 节（A–E 五组），未定处标"待定"。

### A. 数据规整与 schema

- 决策 D1：目标 schema 主字段为「姓名/公司/手机/座机/邮箱/城市/备注」，**手机与座机分列**为独立字段；源独有字段（老系统「合作状态」、备份0812「录入人」、JSON「标签」）保留为**可空附加列**，不丢弃。
- 决策 D3：跨源重复先按「姓名 + 公司」识别疑似同一人；每条字段冲突（手机号/城市/公司简称与全称等）**并列展示并给推荐值**，客户拍板后统一修正，不做静默丢弃。
- 决策 D5：清洗口径——① 公司名仅对**可确证同一家**的归一（如「众合机械」→「众合机械设备有限公司」）并留原写法；城市口语归一到地级市（「深圳那边的」→深圳）；② tag 归一枚举为「客户/供应商/合作伙伴/内部/待定」；③ 测试号与「待补充」占位行**直接剔除并在交付说明留痕**；④ 非联系人事项抽离为独立待办清单；⑤ 归一处理增加「来源文件」字段溯源。
- 决策 D10：溯源分两层——联系人级「来源」列（主来源）+ 字段级冲突溯源（待确认区/交付清单逐字段标「字段名：值A(来源X) vs 值B(来源Y)」）。

### B. 应用形态与能力边界

- 决策 D2：应用形态为「总表**只读展示** + 有限操作入口」：客户总表搜索/筛选/查看 + 「投喂新批次」上传入口 + 简单访问口令；本版不做登录鉴权（列为后续版本规划）。应用另含两项 FDE 新增能力：识别合作意向客户、识别提取待办事项（D6/D7 展开）。
- 决策 D6：合作意向客户用「合作状态 + 标签 + 备注语义」三类信号综合判定；AI **初判 + 人工确认**后才进入「意向客户」展示；展示复用总表按合作状态/标签筛选视图（不另建数据、不另存意向名单）；本版 AI 判定，后续版本可引入规则小模型增强。
- 决策 D7：待办识别与「非联系人事项抽离待办清单」为同一能力；来源**仅限素材中明确出现的非联系人事项**（约饭提醒、回头找电话等），不做泛待办抽取；独立「待办」页、支持勾选完成，本版不做定时提醒推送。
- 决策 D15：应用架构为「静态前端（总表/意向筛选/待办/上传入口/待确认区）+ 轻量后端 + 数据库」；上传/拍板/确认即时入库、页面刷新即见新数据；**仅代码变更才重新部署**（数据更新不触发部署）。
- 决策 D18：操作边界——① 本版**不做只读/操作口令区分**，凡拿到访问口令者均可查看并执行有限操作（人级权限 + 登录鉴权列为后续版本规划）；② 全部修改**留痕**（操作人/时间/字段/旧值→新值）并支持**撤销**；③ **禁止自由增删改**联系人及字段，仅开放「冲突拍板、意向确认/驳回、待办勾选完成、上传新批次」有限操作，字段级编辑由受托方按批处理。

### C. 拍板闭环与待确认区

- 决策 D8：拍板闭环由初版「离线拍板」**修订**为应用内「待确认区」拍板（见 D16）；「拍板后重新部署」表述废弃。
- 决策 D13：受托方完成首期部署并交付可访问 URL；后续数据更新（新批次合并/拍板修正）由受托方代管；采用低成本平台（Vercel 同类），域名/托管成本**客户承担**、配置受托方代管；数据更新不触发部署。
- 决策 D16：冲突拍板（采纳推荐/用A值/用B值）、意向确认（确认意向/驳回）均在应用内「待确认区」点选完成、**即时入库生效**，不再离线往返；数据规模数百数量级、不过度设计。
- 决策 D19：「待确认区」业务责任人——王总本人或其指定的市场部同事均可处理（应用不分人级权限，业务责任人为王总）；「清空待确认区」列为市场部例行职责（每次新批次上传后一周内清完）；验收口径认可：「跨源冲突 100% 已拍板」=「当前批次待确认区清零」。
- 决策 D21：AI 低置信/未识别内容并入「待确认区」，以「原始片段 + AI 候选值（可空）」展示，人工对照补录或确认剔除，**绝不静默丢弃**；待确认区承载三类内容：字段冲突（D3/D16）、疑似重复（D17）、AI 低置信/未识别（D21）。

### D. 后续批次与纠错

- 决策 D4：后续批次走**应用上传入口、任意格式均可**，AI 抽取映射到既有 schema；多模态（图片）可通过调用多模态模型读取（本版落地与否见 D9）；本版**不引入 OCR**（列为后续版本规划）。
- 决策 D9：本版**对扫描件/图片不处理**；首批 `扫描件_补充名单.jpg` 经 FDE 确认为**损坏文件**、无需处理（跳过并在交付说明标注）；「多模态模型直读」仅作后续批次预留能力、不进本版承诺；后续图片/扫描件批次默认请客户先转文字/表格，确需直读时单批协商。
- 决策 D11：老系统按「一次性迁移整理」处理、**不再作为持续数据源**（后续新数据统一走 D4 上传入口）；「合作状态」三值映射：有效=已合作、暂停=暂停合作、待定=有合作意向（不单独以待定等同意向，由 AI 结合标签 + 备注语义综合判定）。
- 决策 D17：新批次 AI 抽取后「**不冲突的新记录直接入库**（带来源标注）」，疑似重复/字段冲突进待确认区拍板；不做全量人工过目。
- 决策 D20：非冲突类字段纠错渠道——主渠道 A：微信/电话直接告知受托方、受托方后台改库（留痕可撤销、页面即时生效）；批量更正可选路径 B：更正较多时打包「更正清单」走上传入口投喂、AI 识别为「修正指令」而非新客户；本版**不做 C**（应用内纠错表单）。

### E. 验收与协作

- 决策 D12：验收标准——提交物 5 项完整可用（① 规整数据 ② 公网应用 ③ 代码与运行说明 ④ 一页非技术说明 ⑤ AI 协作日志）+ 本批全部联系人去重规整 + 跨源字段冲突 100% 已拍板（无静默合并残留）+ 应用公网可访问；经 D19 对齐：冲突已拍板表现为「当前批次待确认区清零」；**不另设量化准确率门槛**。
- 决策 D14：意向确认（确认/驳回）在应用内待确认区完成、即时生效；误判修正走 D18 边界（字段级编辑由受托方按批处理、留痕可撤销）。

## 4. 排除范围

以下事项明确不在本次范围内（均取自 02 第 5 节）：

- **登录鉴权与人级权限/角色区分**：本版只设单一访问口令（D18①）。
- **应用内自由增删改联系人及字段**：仅开放「冲突拍板、意向确认/驳回、待办勾选、上传新批次」有限操作（D18③）。
- **应用内纠错反馈表单**（D20 排除 C）：纠错走微信/电话直达受托方（主）或「更正清单」投喂（可选）。
- **OCR / 图片扫描件处理**：本版不引入 OCR；首批扫描件_补充名单.jpg 已损坏、不处理（D9）。
- **离线拍板 / 随数据更新重新部署**：已废弃（D15/D16）。
- **全量人工过目新批次**：不冲突直入，只对冲突/疑似重复/AI 低置信人工介入（D17）。
- **待办定时提醒推送**：本版只做勾选完成（D7）。
- **老系统持续对接/双向同步**：一次性迁移整理即可（D11）。
- **定量准确率验收门槛**：以提交物 5 项 + 待确认区清零为准（D12）。
- **数据静默丢弃/静默合并**：任何冲突、低置信内容均进待确认区人工处置（D3/D21）。

## 6. 需求清单

软件侧需求（含验收标准）：

1. As a 持口令访问者（王总/市场部）, I want 用单一访问口令进入应用并查看规整后的客户总表（含搜索/筛选）, so that 我能直接使用统一干净、带溯源的客户数据。
   - 验收标准：输入正确口令可访问，错误口令拒绝；总表展示统一 schema 字段 + 「来源」列；搜索/筛选可用；总表内容与规整数据一致（D1/D2/D10/D15/D18）。
2. As a 持口令访问者, I want 在应用内「待确认区」对跨源字段冲突做拍板（采纳推荐/用A值/用B值）, so that 冲突由人最终决定、不做静默合并。
   - 验收标准：冲突以「字段名：值A(来源X) vs 值B(来源Y) + 推荐值」形式逐条展示；点选后即时生效、页面刷新可见（D3/D16/D10）。
3. As a 持口令访问者, I want 对待确认区中的合作意向初判做确认/驳回, so that 意向客户展示准确、供市场部跟进。
   - 验收标准：确认后的联系人出现在意向客户视图，驳回的不出现（D6/D16）。
4. As a 持口令访问者, I want 查看并勾选完成待办事项, so that 素材中抽离的提醒事项（约饭提醒、回头找电话等）不被遗忘。
   - 验收标准：待办页仅含素材中明确出现的非联系人事项；勾选后状态完成；无定时提醒/推送（D7）。
5. As a 持口令访问者（王总/市场部）, I want 通过上传入口投喂新批次（任意格式）, so that 后续多批资料能持续合入总表。
   - 验收标准：上传后 AI 抽取结果按 D17 规则处理——不冲突记录带来源标注直接入库，疑似重复/字段冲突进待确认区；无全量人工过目环节（D4/D17）。
6. As a 持口令访问者, I want 对待确认区中的 AI 低置信/未识别内容补录或确认剔除, so that 无法可靠解析的内容不静默丢失。
   - 验收标准：低置信内容以「原始片段 + AI 候选值（可空）」展示；可补录、可剔除、可保留待定，操作留痕（D21）。
7. As a 持口令访问者, I want 每次修改都留痕且可撤销, so that 误操作可回滚、责任可追溯。
   - 验收标准：每次修改记录操作人/时间/字段/旧值→新值；支持撤销；撤销后页面即时生效（D18②）。
8. As 受托方/维护者, I want 对联系人及字段做批量的、按批的编辑（应用内不开放自由增删改）, so that 字段级纠错可控可审计。
   - 验收标准：应用内无自由增删改入口；受托方后台按批编辑同样留痕可撤销（D18③/D20）。
9. As 王总, I want 收到 5 项提交物（规整数据、公网应用、代码与运行说明、一页非技术说明、AI 协作日志）, so that 交付可验收、后续可运维。
   - 验收标准：5 项提交物齐全可用；一页说明为非技术语言，含交付了什么/怎么用/重要决定/没做什么（D12）。

AI 侧需求并入第 8 章能力清单（AI 能力以"识别/判定 + 人工确认"闭环呈现）。

只测外部行为、不测实现细节：

- **应用行为测试**：

  - 待确认区：冲突拍板 / 意向确认/驳回 / 低置信补录剔除，点选后数据即时变更、刷新可见（D16/D19/D21）。

  - 上传入口：新批次上传后按 D17 分流（直入 vs 进待确认区）；「更正清单」投喂被识别为修正指令而非新客户（D20 路径 B）。

- **验收口径**：提交物 5 项完整可用 + 本批联系人去重规整 + 待确认区清零 + 应用公网可访问（D12/D19）。

## 8. 能力清单与交互方式

AI 能力及明确边界：

| 能力 | 交互方式 | 说明 |
|------|----------|------|
| 多源自由文本/任意格式 → 结构化抽取映射 | 自动 + 人工兜底 | 对上传的任意格式新批次做 AI 抽取映射到既有 schema；不冲突记录自动直入（带来源标注），冲突/疑似重复/低置信进待确认区人工处置（D4/D17/D21） |
| 首批多源资料规整 | 自动 + 人工拍板 | 结构化抽取、按「姓名+公司」识别疑似同一人、字段冲突并列展示给推荐值、清洗归一（公司/城市/tag/测试号占位行），冲突由客户在待确认区拍板（D3/D5/D16） |
| 合作意向客户识别 | 建议+确认 | AI 按「合作状态+标签+备注语义」三类信号综合初判 → 进待确认区人工确认意向/驳回 → 确认后展示；展示为总表按合作状态/标签筛选视图，不另建名单（D6/D11/D16） |
| 待办事项识别提取 | 自动 + 人工勾选 | 识别并抽离素材中明确出现的非联系人事项（约饭提醒、回头找电话等），进独立「待办」页供勾选完成；不做泛待办抽取、不做提醒推送（D7） |
| 修正指令识别（可选路径 B） | 自动 + 人工发起 | 投喂的「更正清单」被 AI 识别为「修正指令」而非新客户，据此批量修正（格式约定待定，D20） |

明确不做：OCR/图片扫描件处理（D9）、多模态直读本版不承诺（D9）、自动回复类能力、自由文本联想补全联系人字段（AI 判定均需人工确认）。

## 9. 数据与知识依赖

- **首批数据源**（input/ 8 份素材，其中 jpg 损坏不处理）：
  - `初步需求和背景.txt`（需求说明，含客户原话）、`备份0812.csv`（10 条含脏数据）、`contacts_export.json`（9 条）、`客户名单-市场部.csv`（13 行）、`客户名单-市场部 (副本).csv`（与正本内容完全相同）、`王总微信发来的.txt`（口语化、字段残缺、夹杂非联系人事项）、`合作伙伴名单(老系统导出).csv`（9 条含「合作状态」）、`扫描件_补充名单.jpg`（**损坏，跳过并在交付说明标注**）。
  - 知识/数据形态：无独立 RAG 知识库；AI 的"知识依赖"即这些投喂素材与既有 schema 映射规则（D4），无需外部语料。
- **规整后主数据**：统一 schema（姓名/公司/手机/座机/邮箱/城市/备注 + 可空附加列 合作状态/录入人/标签 + 来源列）存于应用数据库；主数据是后续展示与合并的基础（D1/D10/D15）。
- **更新频率**：首批一次性规整；后续新批次不定期经上传入口投喂（D4）；数据更新即时入库、不触发重新部署（D15）。
- **工具/API 接入**：无第三方系统对接——老系统仅一次性迁移整理、不再作持续数据源（D11）；应用侧仅需"上传入口文件读取 + AI 抽取"与"数据库读写 + 留痕"能力；低成本托管平台（Vercel 同类，具体平台待定，D13）。
- **权限与审计**：单一访问口令（D18①）；全部修改留痕可撤销（D18②）。

## 10. 质量目标与评估方式

本需求经 D12 明确**不设量化准确率门槛**，以"人工拍板闭环 + 可判定交付物"作为质量评估方式：

| 指标 | 目标值 | 评测方法 |
|------|--------|----------|
| 跨源字段冲突已拍板率 | 100%（当前批次待确认区清零） | 验收时检查待确认区清零（D12/D19） |
| 重复联系人去重 | 本批全部去重规整（无静默合并残留） | 验收比对规整数据与首批素材（D3/D12） |
| 数据可溯源 | 100% 联系人带「来源」列；冲突字段带来源标注 | 抽检总表来源列与冲突记录（D10） |
| 应用可用性 | 公网可访问、口令可访问、操作即时生效 | 验收访问 URL 并实际操作（D12/D13/D15） |
| 提交物完整性 | 5 项提交物齐全可用 | 交付清单核验（D12） |
| AI 抽取/判定质量（内部参考线） | 不设对外量化门槛；低置信内容必须显性进入待确认区而非静默出错 | 抽检新批次分流正确性：不冲突直入、疑似重复/冲突/低置信进待确认区（D17/D21） |

> 说明：质量保证不依赖"AI 第一次就全对"，而依赖 D21 的三类兜底 + D3 的人工拍板闭环；后续若引入规则小模型增强意向判定（D6），再另行定义评测集，本版不承诺。

## 11. 兜底与降级

- **AI 答不上/低置信**：AI 低置信/未识别内容并入「待确认区」，以「原始片段 + AI 候选值（可空）」展示，由王总或市场部同事对照补录或确认剔除——绝不静默丢弃、绝不静默合并（D21/D3）。
- **跨源冲突**：不自动取一；冲突进待确认区并列展示并给推荐值，人工拍板（D3/D16）。拍板责任人缺位风险由"每周新批次后待确认区一周内清零"的例行职责兜底（D19）。
- **AI 判定出错/幻觉**：AI 只从既有字段信号（合作状态/标签/备注语义）做初判，且必须经人工确认/驳回后才展示，杜绝开放式生成联系人数据（D6/D11）；归一仅对可确证同一家的对象执行（D5），防过度归并。
- **新批次投喂内容格式混乱**：由上传入口 AI 抽取 + D17 闸门分流 + D21 低置信兜底三级承接（D4/D17/D21）。
- **用户误操作**：全部修改留痕可撤销（D18②）；应用禁止自由增删改、仅开放有限操作，从入口上限制误改面（D18③）。
- **服务不可用 / 上传失败的降级路径**：素材与 02 未涉及，**待定**（实施时与客户确认，不臆造）。

## 12. 技术选型

> 说明：本章为补全章节。原 spec 在"解决方案概述 / 实施决策"中已散落架构决策（D15 静态前端+轻量后端+数据库、D13 低成本托管平台、D18 单一口令+留痕撤销），但未集中给出可落地的技术选型；以下选型均锚定既有决策与已实现产物，未定处标"待定"，不臆造。

| 层 | 选型 | 锚定决策 / 理由 |
|----|------|----------------|
| 前端 | 原生 HTML + CSS + JavaScript（单页 SPA，**无框架、无构建步骤**） | 客户不懂技术、仅查看与有限操作；数据规模数百级不过度设计（D16）；零构建即可静态托管、部署简单（D15） |
| 后端 | Node.js + 内置 `http` 模块（**不引入 Express 等框架**），同进程托管前端与 REST API | 轻量、零额外依赖；仅提供 API 与静态文件服务（D15）；便于单口令托管平台一键部署 |
| 数据存储 | **JSON 文件数据库**（`data/db.json`）+ 统一审计/撤销底层（lib/store.js） | 数据量小、无需独立数据库服务；文件即库便于受托方按批编辑、备份与溯源；审计流与撤销基于同一 JSON（D15/D18②） |
| 鉴权 | **单一访问口令**（环境变量 `CRM_PASSCODE`，默认 `crm2026`），API 层统一拦截 | 本版不做登录鉴权与人级权限（D18①）；口令在请求头/查询参数校验 |
| AI 能力 | **规则抽取优先**（`PROVIDER=rule`）；LLM 为可插拔增强（`LLM_PROVIDER`+`LLM_API_KEY` 网关，非必需） | 首批以结构化抽取/归一为主，规则可覆盖；低置信内容进待确认区而非静默出错（D21）；LLM 仅增强、不阻断（D4/D6） |
| 托管/部署 | 低成本平台（Vercel 同类，**具体平台待定**，D13） | 公网可访问、客户承担成本、受托方代管配置；仅代码变更触发重新部署，数据更新即时入库不重部署（D15） |
| 编码兼容 | 读取层做 BOM / UTF-8 / UTF-16 / **GBK** 探测（`lib/pipeline.js readText`） | 老系统导出 CSV 实测为 GBK 编码（如 `合作伙伴名单(老系统导出).csv`），需容错避免整表乱码 |

明确待定（不臆造）：具体托管平台与域名、多模态模型选型（D9 本版不引入 OCR）、规则小模型增强意向判定（D6 后续版本）、服务不可用降级路径（D13 实施时确认）。
