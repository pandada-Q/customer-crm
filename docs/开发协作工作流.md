# 开发协作工作流

> 本文写给**继续维护本项目的开发者 / AI 协作者**：一套从"接到需求"到"产出可验收交付"的约定。
> 适用对象：一个人 + AI 助手（或小团队）在无 CI 的条件下持续迭代本仓库。

---

## 1. 需求怎么进来（下指令的姿势）

一条好的需求 = **现象 + 期望 + 素材 + 验收口径**。对 AI 协作者尤其要给出"你可以从哪里复现"。

```text
【现象】上传 xxx.csv 后，秦岚的公司名变成了"深圳市创新"，少了"科技有限公司"
【期望】公司名应完整还原，且以后所有此类文件都不再截断
【素材】07-implementation/../input/备份0812.csv 第 6 行（该行比表头多一列，公司字段被逗号拆开）
【验收】重传该文件：秦岚公司=深圳市创新科技有限公司；同型坏行不静默错位（进待确认）
```

模板要点：

| 要素 | 说明 |
| --- | --- |
| 现象 | 复现步骤 + 实际结果（附数据/截图/报错） |
| 期望 | 正确的行为长什么样 |
| 素材 | 用哪份文件/哪条数据复现（引用具体路径与行） |
| 验收口径 | "怎样算改好了"的可检查描述 |

> 若需求是"多轮打磨"（如"把数据再整理下"），先让协作者**通读现状后给出诊断与方案**，你确认范围（原子决策）再动手——避免一次性铺开大改。

## 2. 任务怎么拆

遵循本仓库沉淀的**八步闭环**（fde 风格）裁剪为本项目粒度：

```
1 信息采集/诊断   → 读代码 + 复现问题，先回答"根因是什么"（如周杰短号案例：先定位清洗丢弃，
                     而不是上来就改）
2 方案确认        → 给出改动文件清单 + 影响面 + 是否动存量数据，人拍板后再写
3 拆 tickets      → 按【数据层 → 后端 API → 前端 → 测试/文档】横向切片；每张票独立可验证
4 实施            → 小步改、每步语法检查；改库先备份
5 验证            → 见下节「验证金字塔」；新增行为必须有测试固化
6 交付            → 重启服务 + 线上只读回归 + 清理临时文件 + 汇报改动/验证/遗留
7 沉淀            → 新踩的坑补进 lib/rules.js 或文档/记忆库
```

### 一张票的理想粒度

```text
标题：CSV 错位列智能对齐（公司名误拆自动还原）
改动：
  - lib/csv.js  新增对齐算法 + unresolved 标记
  - lib/pipeline.js 适配新返回结构（无法对齐 → 待确认低置信）
  - tests/pipeline.test.js 新增 3 场景
验证：npm test 全绿；node -e 手验三场景；不碰真实库
```

### 常见切片顺序（依赖关系）

1. **数据层**（store/rules/clean/csv/intent）→ 2. **管线/合并**（pipeline/merge）→ 3. **API**（server.js）→ 4. **前端**（index/app/styles）→ 5. **测试与文档**。

## 3. 验证怎么打（验证金字塔，从快到慢）

| 层级 | 手段 | 何时做 | 典型命令 |
| --- | --- | --- | --- |
| L1 语法/单元 | `node --check` + `node:test` | 每次改动后 | `npm test`（32 条） |
| L2 内存验证 | 直接用 `node -e` 调 lib（隔离 state） | 逻辑型改动、不想碰库 | 见上例 |
| L3 隔离库端到端 | 起隔离 `CRM_DB` 临时库打 API | 后端行为改动（上传/拍板/状态机…） | 见下方脚本模板 |
| L4 DOM 冒烟 | jsdom 驱动真实服务 | 前端结构改动（新按钮/列/面板） | 临时装 jsdom，跑完即删 |
| L5 线上只读回归 | curl 真实服务 GET 探测 | 每次交付前 | `curl /api/health`、各列表计数 |

### 关键纪律

- **真实库只读**：验证尽量用隔离临时库/只读探测；确需写真实库先 `cp data/db.json data/db.json.bak-YYYYMMDD-原因`。
- **jsdom 冒烟注意事项**（本项目多次踩坑）：
  - 必须注入 `w.fetch = (u,o)=>fetch(new URL(u,BASE),o)`（Node fetch 要绝对 URL）
  - 登录按钮的 onclick 在 app.js 末尾绑定，脚本要 `waitFor(() => typeof $('#loginBtn').onclick === 'function')` 再点
  - 助手/清空等 POST 一律 mock，防止打真库/花 token
  - jsdom 用 `npm i --no-save jsdom`，跑完删 node_modules 与 package-lock.json
- **input/ 素材是测试的地基**：集成测试断言依赖其文件与内容，**不要增删改 input/ 下文件**；手动测试用的自由文本放仓库根（如 `手动测试-口语文本.txt`，已在 .gitignore）。
- **测试环境变量**：`tests/app.test.js` 已设 `LLM_PROVIDER=rule`，任何新测试不要去掉，防止测试真调大模型。

## 5. 本仓库的"易错点清单"（历史踩坑，改前必读）

1. **Windows + git-bash 路径坑**：别用 `CRM_DB="$(pwd)/data/db.json"` 启动——`/c/Users/...` 会被 `path.resolve` 解析成 `C:\c\Users\...` 导致库"为空"。直接 `node server.js`（内部用 `__dirname`）。
2. **杀服务进程**：Windows 上 POSIX `pkill` 杀不掉原生进程；用 PowerShell `Get-NetTCPConnection -LocalPort 4173` → `Stop-Process`。
3. **CSV 是确定性解析**：CSV/JSON 不调大模型；只有 `.txt` 自由文本走 DeepSeek（异常行可选送 LLM）。所以 CSV 质量问题的修复点永远在 `lib/csv.js`/`clean.js`，别去改 prompt。
4. **"智能对齐"只修"多一列"**：行比表头多 1 列才尝试合并相邻格并按列类型校验；多 2 列以上直接进待确认，不做冒险猜测。
5. **短号保留 ≠ 放行**：10 位短号保留入库但仍判低置信待人工补全；判定函数在 `lib/intent.js`，别把 `isLowConfidenceContact` 的条件改松。
6. **字段清洗迁移字段**：`clean.repairFieldFormat()` 会把手机号从城市列搬回，写新解析路径时记得调用它。
7. **todo 状态机**：不要直接设 `done`；用 `store.setTodoStatus`；新增状态需同步 store.js 的 TODO_STATUS、server 校验、前端按钮映射三处。
8. **上传任务与清空竞态**：`/api/dev/clear` 会 cancel 后台任务；若改清空逻辑，保留对 `jobs` 的取消。
9. **/api/config 与 DEV_TOOLS**：清空按钮默认隐藏，只有 `DEV_TOOLS=1` 时 server 注册端点且前端拉 config 显示；测试"按钮隐藏"要确认服务未开 DEV_TOOLS。
10. **.env 不入库**：Key/口令只放本地 .env（gitignore），模板在 `.env.example`。
11. **模型能力边界（DeepSeek 纯文本）**：本项目 AI 走 DeepSeek `deepseek-chat` **文本模型，不支持多模态解析/OCR**，图片（如 `input/扫描件_补充名单.jpg`，可能已损坏）**不会被读取内容**——它只是被"识别为不支持格式"跳过。也**尚未引入 MCP/外部工具**：所有能力=确定性规则 + 单一大模型文本调用。改 AI 行为前先确认：是否涉及读图/OCR（需要换多模态模型或另接 OCR，成本另算）、是否要新增工具调用（需引入 MCP，当前无）——不要假设模型"能看图"。

## 6. 交付检查单（每次交付前过一遍）

- [ ] `npm test` 全绿；本次新增行为有对应测试固化
- [ ] 真实库改动前有 `db.json.bak-*` 备份；验证未污染真实数据
- [ ] 服务已重启且 `curl /api/health` 正常（若改动 server.js/lib）
- [ ] 无临时残留：`_*.tmp.js`、`node_modules`、`package-lock.json`（jsdom 临时装过要删）
- [ ] 页面冒烟通过（涉及前端时）
- [ ] 汇报包含：改了什么（文件级）、验证结果、遗留事项/边界、是否需要用户拍板点
- [ ] 新踩的坑已沉淀（rules.js / 本文档 / 项目记忆库）

> 与 AI 协作者长期协作时，把"新坑"追加进本文档第 5 节，下次就少走弯路。
